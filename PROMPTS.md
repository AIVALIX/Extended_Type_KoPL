# Prompts and worked examples

This file collects the LLM prompts used by ETK + APF + PA-CIR in one place,
separately from the source code, together with worked examples taken from the
actual evaluation runs reported in the paper.

Everything here is generated by the code in this repository; the templates are
reproduced verbatim from the following locations.

| Prompt | Where it is built |
|---|---|
| Phase 1 — Type-KoPL generation | [`app/pipeline/extended_type_kopl/pipeline.py:1957`](app/pipeline/extended_type_kopl/pipeline.py#L1957) |
| Phase 4→1 — APF correction | [`app/pipeline/extended_type_kopl/pipeline.py:2364`](app/pipeline/extended_type_kopl/pipeline.py#L2364) |
| Phase 3b — PA-CIR reranker | [`app/pipeline/extended_type_kopl/reranker.py:133`](app/pipeline/extended_type_kopl/reranker.py#L133) |
| Anchor probe (evidence, not a prompt) | [`app/pipeline/extended_type_kopl/pipeline.py:2224`](app/pipeline/extended_type_kopl/pipeline.py#L2224) |
| Real-edge set for the probe gate | [`app/pipeline/extended_type_kopl/pipeline.py:2264`](app/pipeline/extended_type_kopl/pipeline.py#L2264) |
| Cypher trial (`LIMIT 5`) | [`app/pipeline/extended_type_kopl/pipeline.py:3500`](app/pipeline/extended_type_kopl/pipeline.py#L3500) |
| Schema-level diagnosis | [`app/pipeline/extended_type_kopl/pipeline.py:2290`](app/pipeline/extended_type_kopl/pipeline.py#L2290) |

At most three LLM calls are issued per question: one Phase 1 generation, one
Phase 3b reranking, and at most one Phase 4→1 correction. The anchor probe and
the Cypher trials are plain database queries and involve no LLM.

## 1. Phase 1 — Type-KoPL generation

Placeholders in `{braces}` are filled per question. `{available_relations}` is
the KG's relation inventory in `(src_type)-[RELATION]->(tgt_type)` form, and
`{examples}` is a few-shot block selected per KG (and optionally retrieved
per question by the few-shot pool).

```text
Convert this question into an Atomic Type-KoPL program.

Question: {question}
{entity_info}

Available node types: {type_list}

{available_relations}
{filter_info}{answer_type_info}
CRITICAL RULES:
1. Each operation represents ONE HOP in the path. For N-hop queries, provide exactly N operations.
2. Each operation specifies: src_type, tgt_type, relation, anchor_name (if applicable)
3. For PATH queries: operations MUST chain type-consistently:
   op[0].tgt_type == op[1].src_type, op[1].tgt_type == op[2].src_type, etc.
   VERIFY: Check each (src_type)-[relation]->(tgt_type) triple against Available Relations before outputting.
4. For INTERSECTION queries: each operation has its own anchor_name, final_operation="intersection"
5. Break down the question step by step. Each operation = one hop. Do NOT combine multiple steps into one semantic description.
6. Build path from anchor to answer. The relation nearest to [anchor] in the question is the FIRST hop, not the last.

{examples}

Return a JSON object with operations array, final_operation, answer_type, and optionally filters/query_key/verify_value/verify_op/select_mode/select_entity_a/select_entity_b.
```

`{entity_info}` carries the anchor resolved from the question:

```text
Known entity: irinotecan
Target type (what the question asks for): Cancer
```

## 2. Phase 4→1 — the APF correction prompt

This is the prompt APF modifies. It fires only when Phase 4 execution returns
an empty set, and it runs at most once per question.

```text
Your previous Type-KoPL program for this question produced no valid paths in the knowledge graph.

Question: {question}
{entity_info}

Available node types: {type_list}

{available_relations}

Your previous answer:
{serialized_failed_kopl}

Diagnosis (why it failed):
{diagnosis}

Please generate a CORRECTED Atomic Type-KoPL program. Fix the type names and relation hints based on the diagnosis above. Use only types that appear in "Available node types".

{examples}

Return a JSON object with operations array, final_operation, and optionally filters.
```

### What APF changes

The template is the same with and without APF. **APF changes what goes into
`{diagnosis}`.** Without APF the block holds only schema-level information:

```text
Cypher execution returned 0 results for anchor 'irinotecan' with paths: Drug -[TREATMENT]<- Cancer. The entity may have a different name in the KG, or the relation path is wrong.
Schema info:
(Drug)->(Cancer): OK (2 relations)
```

Note the failure mode this exposes: the schema diagnosis says the type pair is
fine, because at the *schema* level `Drug -[TREATMENT]-> Cancer` does exist.
The LLM is told only that something went wrong, not what the anchor actually
has, so it tends to regenerate the same program.

With APF, the anchor probe result is appended:

```text
Cypher execution returned 0 results for anchor 'irinotecan' with paths: Drug -[TREATMENT]<- Cancer. The entity may have a different name in the KG, or the relation path is wrong.
Schema info:
(Drug)->(Cancer): OK (2 relations)

Anchor instance probe:
Anchor 'irinotecan' actually has these edges in the KG:
  -[TREATMENT]->(CancerAlias)  [1 edges]
```

Now the contradiction is explicit: the schema allows `Drug → Cancer`, but this
particular anchor only reaches `CancerAlias`. That is the instance-level
evidence the schema cannot supply.

### Anchor probe

One Cypher query per anchor, reused within the correction round and shared
with PA-CIR:

```cypher
MATCH (a)
WHERE a.name = $name OR toLower(a.name) = toLower($name)
WITH a LIMIT 1
MATCH (a)-[r]-(n)
WITH type(r) AS rel,
     CASE WHEN startNode(r) = a THEN 'out' ELSE 'in' END AS dir,
     head(labels(n)) AS nbr_label
RETURN rel, dir, nbr_label, count(*) AS cnt
ORDER BY cnt DESC
LIMIT 20
```

Rendered as, at most 20 rows ordered by descending count:

```text
Anchor '<name>' actually has these edges in the KG:
  -[REL_A]->(LabelX)  [12 edges]
  -[REL_B]<-(LabelY)  [3 edges]
```

If the anchor has no edges at all, the probe returns instead:

```text
Anchor '<name>' has NO edges in the KG (entity may not exist under this name or is isolated).
```

## 3. Phase 3b — the PA-CIR reranker prompt

```text
You are a knowledge graph expert. Select the single best path that answers the question.

Question: {question}

{kopl_text}
Candidate paths:
{paths_text}
IMPORTANT:
- Do NOT simply match relation names to words in the question. Relation names in the KG may use abbreviations or different terminology than the question.
- Consider what each relation semantically means in the context of the knowledge graph.
- The query plan hints are approximate and may not exactly match any relation name in the KG.
- Think step-by-step about which path correctly captures the reasoning chain needed to answer the question.{trial_instruction}
- If NONE of the candidate paths can correctly answer the question (wrong relation types, wrong direction, semantic mismatch), set `all_invalid=true` instead of forcing a selection.

Return the index (0-indexed) of the best path, or set all_invalid=true if no candidate is valid.
```

### What PA-CIR changes

Two things: the candidate list is filtered before it reaches the prompt, and
each surviving candidate is annotated with what it actually returns.

Baseline `{paths_text}` — names only:

```text
0. drug -[enzyme]-> gene/protein
1. drug -[target]-> gene/protein
2. drug -[transporter]-> gene/protein
3. drug -[carrier]-> gene/protein
```

PA-CIR `{paths_text}` — survivors of the real-edge filter, each trial-executed
with `LIMIT 5`:

```text
0. drug -[enzyme]-> gene/protein  → Example results: BCHE, CYP3A4, CYP3A43, CYP3A5, CYP3A7
1. drug -[target]-> gene/protein  → Example results: ADRA1A, ADRA1B, ADRA1D, ADRA2A, ADRA2B
```

A candidate that survives the filter but whose trial returns nothing is kept,
not dropped, and is marked so the reranker can tell the two situations apart:

```text
2. drug -[transporter]-> gene/protein  → (no trial results; path may be sparse for this anchor)
```

`{trial_instruction}` is appended only when trial samples are present:

```text
- IMPORTANT: Each candidate path shows "Example results" from the actual knowledge graph.
- Compare the example results against what the question is asking for.
- Choose the path whose example results best match the expected answer type.
```

The trial query is the candidate's own Cypher with `LIMIT 5` appended and no
`ORDER BY`, so the five samples are whatever the engine returns first.

## 4. Worked examples

Both cases below are real records from the ablation runs with
`gpt-4.1-mini` (`result/etk_ablation_20260512/`). Each shows the baseline, the
`+APF` configuration, and the `+PA-CIR` configuration on the same question.

### 4.1 PA-CIR rescues a semantic-mismatch failure

*PrimeKGQA 1-hop — "Which enzymes are targeted by Moxisylyte?"*

Gold: `BCHE, CYP3A4, CYP3A43, CYP3A5, CYP3A7`

| Config | Selected path | Predicted |
|---|---|---|
| baseline | `drug -[target]-> gene/protein` | `ADRA1A, ADRA1B, ADRA1D, ADRA2A, ADRA2B, ADRA2C` |
| `+APF` | `drug -[target]-> gene/protein` | `ADRA1A, ADRA1B, ADRA1D, ADRA2A, ADRA2B, ADRA2C` |
| `+PA-CIR` | `drug -[enzyme]-> gene/protein` | `BCHE, CYP3A4, CYP3A43, CYP3A5, CYP3A7` ✅ |

The question contains the word "targeted", so the baseline reranker picks the
`target` relation on lexical similarity. That path *executes successfully* — it
returns six adrenergic receptor genes — so nothing signals a failure, and APF
never fires: there is no empty result to correct. Only PA-CIR helps, because
only PA-CIR shows the reranker that `target` yields receptors while `enzyme`
yields the CYP/BCHE enzymes the question asks for.

This is the division of labour the paper argues for: a wrong-but-executable
path is a selection-stage problem, and correction-stage machinery cannot see
it.

### 4.2 APF rescues an empty-query failure

*PcQA — "What types of cancer can irinotecan be used to treat?"*

Gold: `colorectal cancer`

| Config | Selected path | Predicted |
|---|---|---|
| baseline | `Drug -[TREATMENT]<- Cancer` | *(empty)* |
| `+PA-CIR` | `Drug -[TREATMENT]<- Cancer` | *(empty)* |
| `+APF` | `Drug -[TREATMENT]<- CancerAlias` | `colorectal cancer` ✅ |

Phase 2 enumerated only two candidates, `Drug -[TREATMENT]<- Cancer` and
`Drug -[INDUCE_TO]<- Cancer`, and **neither is reachable from this anchor** —
`irinotecan` has exactly one edge in the KG and it ends at `CancerAlias`, not
`Cancer`. PA-CIR cannot fix a candidate set in which no candidate works: its
filter is subtractive, so when every candidate fails the real-edge check the
filter is skipped and the original ranking stands. Regeneration is the only
way out, and the probe gives the LLM the fact it needs — that the anchor's
`TREATMENT` edge points at `CancerAlias`.

You can reproduce the probe output for this anchor from the shipped CSVs
without starting Neo4j:

```text
Anchor 'irinotecan' actually has these edges in the KG:
  -[TREATMENT]->(CancerAlias)  [1 edges]
```

## 5. Reproducing these examples

The per-question records, including `candidate_paths`, `selected_paths`,
`predicted_entities` and the `processing_log`, are written to JSONL by the
evaluation runner (see Section 6 of [README.md](README.md)). Both cases
above come from:

```text
result/etk_ablation_20260512/gpt41mini/{baseline,apf,pa_cir}/
    primekgqa_one_hop/extended_type_kopl_one_hop.jsonl
    pcqa_all/extended_type_kopl_all.jsonl
```

To regenerate those runs, use the ablation flag combinations in Section 5.2 of
the README. The `processing_log` field of each record shows the phase-by-phase
trace, including whether the correction round fired and what the anchor probe
returned.
